Detailed Explanations

1. Voice Commands Toggle in Charades — NOT A BUG

What QA reported: "The Voice Commands toggle is still fully visible and can be turned on in the Charades setup screen. If enabled, the game would try to listen for voice commands, which contradicts the core rule of Charades (silence)."

What actually happens in the app: When a player selects Charades mode, the voice toggle is automatically disabled:

  • It becomes greyed out (faded to 35% visibility)
  • It cannot be clicked or tapped — touch/click events are blocked
  • It is automatically switched OFF

The toggle remains visible on screen (faded) for layout consistency, but it is completely non-interactive. A player cannot turn it on. The QA tester may have confused "visible in the interface" with "clickable and functional."

2. Tilt Controls Toggle in Charades — NOT A BUG

What QA reported: "The Tilt Controls toggle is available and can be enabled in Charades mode."

What actually happens: Identical to voice — the tilt toggle is greyed out, non-clickable, and automatically turned off in Charades mode. It cannot be enabled by the player.

3. Dark Background on Wide Desktop Screens — BY DESIGN

What QA reported: "When opened on a wide monitor (1920px+), there are black bars on left and right. The game content doesn't fill the full width."

Why this is intentional: Wham Bam is a mobile party game — players hold the phone on their forehead or pass it between friends. The interface is designed for phone screens (360-430px wide). On desktop:

  • The dark background fills the entire browser window edge-to-edge
  • Game cards and buttons center themselves at mobile-friendly widths
  • This is the standard approach for all mobile-first games viewed on desktop (same as most app stores, mobile games, etc.)

Stretching the UI to 1920px would make buttons and text absurdly large and degrade the visual design. No change needed.

4. "Perfect Round" Achievement Not Triggering — NEEDS MORE INFO

What QA reported: "A round was completed with exactly 5 correct answers and 0 skips, but the achievement badge was not unlocked."

Our investigation: We audited the achievement code. The logic checks: "Did the player get 5 or more correct answers with zero skips in this round?" This is exactly what the description says ("5+ correct, zero skips").

The code is correct. Possible explanations for QA's experience:

  • The round may have been quit manually before the timer expired (achievements only trigger when a round ends naturally)
  • A skip may have been triggered accidentally (e.g., by tilt sensor or voice) without the tester noticing
  • The test may have been run on a cached version before the latest deployment

Request to QA team: Please provide exact reproduction steps — which game mode, which timer length, how many rounds, and confirm the round ended via timer (not manual exit).

What We Fixed

Fix 1: "Forgot Password?" Link Now Hidden on Sign-Up Tab — FIXED

The problem: When a new user is creating an account (Sign Up tab), they saw a "Forgot password?" link. This doesn't make sense — you can't forget a password you haven't created yet. It was confusing.

What we changed: The "Forgot password?" link now only appears on the Sign In tab, where it's relevant. When a user switches to Sign Up, the link disappears. When they switch back to Sign In, it reappears.

Why this matters: Cleaner user experience. No confusing options that don't apply to the current action.

Fix 2: Screen Readers No Longer Announce Decorative Emojis — FIXED

The problem: The home screen has floating decorative emojis in the background (party face, alien, robot, dancer, unicorn, sparkle symbols). Screen readers (used by visually impaired users) were reading these aloud as meaningless noise: "party face... alien... robot... dancer..."

What we changed: Added an accessibility attribute (aria-hidden) to the containers holding these decorative elements. This tells screen readers: "skip this, it's just decoration." The emojis still appear visually for sighted users.

Why this matters: Accessibility improvement. Visually impaired users now get a cleaner experience without random emoji characters being read to them.

Fix 3: Password Minimum Raised from 6 to 8 Characters — FIXED

The problem: Sign-up allowed passwords as short as 6 characters. Modern security standards recommend at least 8 characters.

What we changed:

  • New accounts must now use at least 8 characters for their password
  • Password reset also requires minimum 8 characters
  • Error message updated: "Use at least 8 characters."

Important: Existing users with 6 or 7 character passwords can still sign in — they are NOT locked out. The new minimum only applies to new sign-ups and password resets.

Why this matters: Better security for user accounts. 8+ characters is the industry standard used by major services.

Items Planned for Future Updates

"Confirm Password" Field on Sign-Up

What QA suggested: Add a second password field so users can confirm they typed it correctly.

Our response: Valid suggestion. However, the app already has a working "Forgot Password" recovery flow, which handles the case where a user mistypes their password. We will add the confirm field in a future auth UX update.

Skip-Navigation Link for Keyboard Users

What QA noted: No "skip to main content" link for keyboard/screen-reader navigation.

Our response: Will add in the next accessibility improvement pass. The app already has a <main> landmark wrapper, proper button semantics, and keyboard navigation on all interactive elements.
